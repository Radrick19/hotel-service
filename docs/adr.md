# ADR: ключевые решения

## 1. Четыре приложения и общий модуль

**Решение.** Я разделил hotel Service на Maven-модули: Eureka, Gateway, Hotel, Booking запускаются отдельными JVM в контейнерах Docker Compose. Common — библиотека, а не пятый сервис. Общие DTO ошибок, servlet-безопасность, trace-фильтр и JWT-конфигурация вынесены в Common. DTO представлены Java records, сущности — JPA + Lombok; MapStruct не нужен для коротких явных преобразований.

**Причина.** Это выполняет распределённую архитектуру задания без дополнительных компонентов. Gateway использует WebFlux, бизнес-сервисы — MVC/JPA. Common с servlet-зависимостями не подключается в Gateway. У инфраструктурных Eureka и Gateway нет предметных данных и собственной БД.

## 2. JWT проверяется на Gateway и сервисах

**Решение.** Для JWT использую HS256 с общей конфигурацией секрета; issuer hotel-booking; пользовательский JWT живёт 3600 секунд, сервисный INTERNAL — 60 секунд. Пароли BCrypt. Проверки ролей на методах контроллеров, права на личную бронь — по user_id.

**Причина.** Прямой доступ к backend не обходит авторизацию. INTERNAL — техническая роль для серверных запросов, публично пользователь может получить только USER или назначенную администратором ADMIN. Внутренние операции дополнительно требуют X-Internal-Key и исключены из маршрутов Gateway. Для этого проекта использую общую конфигурацию JWT без отдельного сервера авторизации.

**Ограничение.** JWT остаётся действительным до истечения срока после изменения роли/пароля; отдельный механизм отзыва не входит в задание.

## 3. Сага и последовательность локальных транзакций

**Решение.** Сначала фиксирую PENDING в локальной БД. Отдельно выбирается и фиксируется room_id. Следующий шаг блокирует запись Booking, вызывает confirm и фиксирует CONFIRMED либо CANCELLED с компенсацией. Транзакция Booking может удерживать собственную строку во время ограниченного по времени HTTP-вызова; Hotel фиксирует свой слот в независимой транзакции. JTA/XA не используются.

**Причина.** Блокировка сериализует повторную обработку одного bookingId. Заранее сохранённый room_id позволяет повторить confirm после прерывания процесса, даже если Hotel уже занял номер. Восстановление не подбирает другой номер, пока есть сохранённый выбранный номер.

**Компенсация.** При ошибке вызывается release; при недоступности сохраняется release_pending. Периодическая задача повторяет release и продолжает PENDING старше 30 секунд. Нет ложного сообщения об освобождении при неудаче: клиент видит releasePending. Отмена пользователем тоже идемпотентна. При постоянной недоступности Hotel слот остаётся занятым до успешного восстановления связи.

**Ограничение.** H2 in-memory теряет состояние при остановке JVM. Сага восстанавливается из сохранённых записей в пределах жизни БД, но не обеспечивает долговечность после утраты H2. После независимого перезапуска одного бизнес-сервиса возможна рассинхронизация; для демонстрации перезапускаются оба, как предусмотрено in-memory заданием.

## 4. Идемпотентность и запоздалый confirm

**Решение.** В качестве Booking.id использую UUID requestId клиента. Повтор проверяет владельца и значимые поля. Конкурентная вставка защищена PK; проигравший поток читает существующую запись в новой транзакции. Slot.id — детерминированный UUID от строки bookingId:roomId. Поэтому автоматический подбор после конфликта имеет отдельный ключ для каждого кандидата, а повтор одного кандидата сохраняет прежний ключ.

**Причина.** Компенсация одного кандидата не затрагивает другого и не снимает бронь чужого запроса. Hotel release сохраняет released=true, даже если confirm ещё не пришёл. Поздний confirm с этим ключом получает 409. Запись об освобождении не удаляется: удаление позволило бы позднему запросу занять номер повторно.

## 5. Планирование и конкурентность

**Решение.** Для рекомендаций отбираю номера по условиям: available=true, нет пересечения активных слотов, необязательный hotelId, сортировка times_booked ASC, id ASC. Автоподбор берёт первый элемент. При конфликте выполняет компенсацию и повторно запрашивает актуальный список, не больше десяти выборов за запрос. Все операции изменения номера/слота используют PESSIMISTIC_WRITE на одной строке Room.

**Причина.** Это простой алгоритм равномерного заполнения из задания. Повторная проверка Hotel авторитетна: список рекомендаций является снимком и может устареть. Соседние даты не конфликтуют. Разные номера блокируются независимо.

**Ограничение.** При высокой конкуренции на непересекающиеся периоды несколько клиентов могут получить одинаковый снимок рекомендаций; алгоритм не обещает глобально идеальную балансировку. Статистические прогнозы не используются.

## 6. Устойчивость HTTP и ошибки

**Решение.** Для HTTP-вызовов настраиваю connect/read timeout и ограниченный Retry с увеличением задержки; 4xx не повторяются. Resilience4j CircuitBreaker защищает confirm и получение рекомендаций. Release обходит открытый breaker, иначе компенсация могла бы блокироваться вместе с основным вызовом. После исчерпания попыток компенсация возвращается планировщику.

**Причина.** Тайм-аут не доказывает, что удалённая транзакция не успела выполниться. Поэтому release вызывается и при неясном результате confirm. 404 на release трактуется как отсутствие ресурса, который нужно освобождать.

**Ошибки и логи.** Общий ErrorDto, явные HTTP-статусы, event и bookingId в логах, X-Request-Id и traceId для корреляции. Для отказа при создании брони возвращается сохранённое CANCELLED-представление, чтобы клиент мог проверить результат и необходимость повторной компенсации.

## 7. Запуск в Docker Compose

**Решение.** Для сборки использую один многоэтапный Dockerfile: Maven собирает проект в образе JDK 21, затем выбранный JAR копируется в JRE-образ. Compose запускает четыре контейнера в общей сети; Common остаётся библиотекой. Имена регистрации Eureka переопределяются именами контейнерных сервисов, адрес реестра — http://eureka-server:8761/eureka/.

**Причина.** Для запуска требуется только Docker с Compose. HTTP healthcheck и depends_on задают порядок запуска. Проверка готовности приложения не гарантирует немедленного обновления кэшей discovery, поэтому первые запросы могут требовать ожидания. H2 остаётся in-memory; постоянные тома и дополнительные сервисы не вводятся.

**Тестирование.** JUnit/MockMvc/WebTestClient сохраняются; их можно запускать в сборочном образе. Команды Compose и ручные сценарии проверки привожу в README.
